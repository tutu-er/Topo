## 3. 日志口径：为什么 trace 最后一行仍有 gap

`prototype.py:406--420` 在 master 求解后更新全局 LB，随后马上检测是否收敛；若收敛，直接 break。完整 trace 追加发生在后面的 `prototype.py:465`，因此最后一次“只求 master、无需再求 LP”的认证步骤没有保存。

输出 `iterations` 是 `len(cuts)`，应解释为子问题求解/割的数量，不能解释成 master 调用数。`elapsed_seconds` 包含最后认证步骤，单独求和 trace 中的 `master_seconds + subproblem_seconds` 不等于总耗时，还缺建模、Python 拼接、可行解重建和末次认证。

对新的较大实验，宜由独立包装器记录每次 master 调用的时间、dual bound、status 和 cut count，保留 terminal event。绘制收敛曲线时必须从最终结果补上最终认证点，否则会误画成带正 gap 终止。此为日志完整性问题，并不是已发现的最优性判定错误。

## 4. 和“直接用求解器”的区别

两者底层都使用 SciPy 接口的 HiGHS。原方法一次提交包含结构、权重、乘积线性化和残差的完整 MILP；HiGHS 在一次求解里联合处理松弛、分支、割和可行解。当前 Benders 是 Python 外循环：每轮提交一个结构 master MILP，再解一个连续 LP，提取一个聚合割后重新提交 master。

在相同数据、支撑域、边界和目标、并都完成认证时，它们应得到同一个单步最优目标（可能存在多重最优支撑）。Benders 改变求解组织方式，不改变统计模型，也不会在同一已认证目标上产生“更好的最优值”。二者都仍服务于当前前向算法的一次扩展，没有因此升级为全树联合全局优化。

当前实现没有持久化求解器实例、MIP start、单树回调或 LP basis 复用。虽然预建矩阵及历史 Benders 割被保留，但 `solve_master` 每次重新调用 `milp`，前一棵搜索树不会被继续使用；`solve_subproblem` 每次调用 `linprog`，没有把上一轮最优基传回。微型例子下，每个 master 约 10--13 ms，LP 约 4--8 ms，调用开销与实际求解同量级。

## 5. 扩规模的限制与可验证假设

令终端数 n、旧支撑数量 K、场景数 S、标量残差数 N、上三角乘积数量 p=n(n+1)/2。当前代码规模为：

- Master：n+3K 个二元变量，p 个连续 y 与 1 个 theta；每次 LP 加一条聚合最优性割。
- 子问题：2(K+1)+2p+Sn+N 个连续变量，2N+6p 条显式不等式（不计变量边界）。
- 每个电压残差依赖该终端对应的整行 R/X 乘积，稀疏系数数量随 N*n 增长，并另外依赖旧支撑的成员关系。
- 固定 n 增大样本数时，master 基本不变，但每轮 LP 都变大；这正是可测试 Benders 优勢的方向，并不保证优势出现。
- 增大 n 时，乘积变量是 O(n^2)，合法支撑的最坏数量仍为指数级。层次约束可裁剪域，但 Benders 没有消除原来的组合难度。
- 已有 trace 在终止前 LB 恒为 0，说明这些例子前几条割对尚未评估区域的全局下界帮助有限；不能外推说所有大实例都如此，也不能把无噪声近零 UB 的提前结束当作强下界表现。
- 场景共享 R/X 参数，当前 LP 是联合求解。不能直接拆成各场景自由拟合独立 R/X 的多个 LP，再称作原模型的精确分解。

因此，合理的大样本/多终端比较应同时报告：同输入下的完整调用时间、达到相同容差的成功比例、未完成时的 UB/LB 与停止原因、LP/主问题次数、首次达到最终/高质量 UB 的时间、最终认证时间。超时与缺少可行解必须保留。建议分别变化 n 与 N，进行预热和交替顺序的重复计时，并避免并发求解相互争抢计算资源。

现有四例足以支持“独立原型与直接 MILP 在微型实例上等价并可认证”，不足以支持“Benders 普遍提速”“多终端下仍快速”或“结构恢复率提高”。
